How blueprint works

Fourteen markdown files that change how Claude thinks about your code. No software runs. The whole idea is that Claude has to stop and ask you before it does anything that matters.

The one idea

Every skill has a gate — a hard stop where Claude presents what it worked out and waits for you.

That's the entire point. Everything else exists to make the gate land in a useful place.

Without a gate, Claude reads your code, decides on a plan, and starts editing — and you find out what it thought only by reading the diff afterwards.

With one, you see the reasoning while it's still cheap to change.

Two chains

Skills hand work to each other in a fixed order. Each one produces something the next one is contractually required to accept.

Building something new

spec-interview→ ideate→ architect→ design→ scaffold

Decide the approach, work out the pieces, define the interfaces, then write the files. Only the last step touches your disk.

Fixing something that exists

review-architecture code-review review-depth→ refactoring-plan→ refactor

Diagnose first, in three different ways. Turn the findings into an ordered plan. Then execute it — and only then does anything change.

Why three review skills

They sound alike and they are not. Each measures a different cost.

review-architecture

What it costs to change the code. Boundaries, dependency direction, how many files you touch to add a feature.

review-depth

What it costs to understand it. Whether modules hide real complexity or are thin wrappers you read straight through. Looks for 13 specific problems — hidden call ordering, names that describe machinery, comments covering for bad names.

code-review

Whether the code is correct, file by file. Bugs, conventions, clarity.

All three write findings with ID tags — AR-*, DM-*, CR-* — and refactoring-plan merges them. Two tags pointing at the same line are usually one problem seen twice, so it folds them into a single step.

Pressure packs

A pack is a checklist taken from one engineering book, stored in principles/. It loads at a skill's gate when its condition is true, and adds checks the skill has to satisfy before it presents to you.

One is installed. It comes from Working Effectively with Legacy Code and fires on refactor when the code being changed has no test reaching it.

It adds two questions refactor never asked: is this seam here to watch something or to replace something, and what condition later removes it?

Packs are pressure, not policy. If a pack disagrees with your shared principles, it has to say so at the gate rather than quietly winning. To remove one, delete the file.

A pack only gets in by proving itself. It's pasted into the gate it claims to improve, and the result is compared against the same task run without it. Three of the four candidates never earned a place.

The checker

Run python3 tools/registry_check.py --check after changing any skill. Exit 0 means clean.

It rebuilds the index, confirms every skill still has a gate and a contract, and catches the mistake this repo kept repeating: adding a skill without telling the older one it now has a neighbour. Every collision ever found here was one-sided like that.

To compare two skills fairly it needs to know what each one produces — so every skill states it in its own file. It used to guess from wording, which meant a reworded description could quietly drop a skill out of the check while the tool still said everything was fine. Now a missing statement is a failure, not a free pass.

A check that only ever passes is the same as no check. This one was deliberately broken twice — once by deleting a declaration, once by removing a skill's mention of its neighbour — to confirm it catches both before being trusted.

Four workflows, fourteen skills, one pack. Everything is markdown — you can read and change any of it.
